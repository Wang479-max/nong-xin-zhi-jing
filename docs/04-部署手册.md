# 农芯智境生产部署与运维手册

本文面向腾讯云 CVM Ubuntu 22.04 LTS、2 核 2 GB 内存、40 GB 系统盘，域名为 `www.nongxinzhijing.site`。配置适合竞赛演示、联调和低并发试运行；正式商业运营应迁移到腾讯云托管 PostgreSQL、Redis 和对象存储，并增加多可用区与监控告警。

## 1. 上线架构与边界

```text
浏览器 -> 80/443 Nginx -> 127.0.0.1:3000 Node.js 22
                                  |-> PostgreSQL 127.0.0.1:5432
                                  `-> Redis      127.0.0.1:6379
```

- Nginx 是唯一公网入口，负责 HTTPS、WebSocket、静态资源缓存和登录限流。
- 应用在宿主机部署时只监听 `127.0.0.1:3000`。容器内监听 `0.0.0.0:3000`，但 Docker 仅映射到宿主机 `127.0.0.1:3000`。
- PostgreSQL 的 5432 和 Redis 的 6379 不发布到公网，也不要加入腾讯云安全组入站规则。
- PostgreSQL 保存 SaaS 用户、组织、授权和订单；`USER_DATA_PATH` 保存尚未迁移的旧业务 JSON 数据，两者都必须持久化和备份。

## 2. 腾讯云与域名准备

### 2.1 DNS

在腾讯云 DNSPod 添加以下 A 记录，并等待解析生效：

| 主机记录 | 记录值 |
| --- | --- |
| `@` | CVM 公网 IPv4 |
| `www` | CVM 公网 IPv4 |

验证：

```bash
dig +short nongxinzhijing.site
dig +short www.nongxinzhijing.site
```

截图中的香港地域服务器通常不要求中国大陆 ICP 备案；若迁移到中国大陆地域，公开网站上线前应按腾讯云要求完成备案。域名与证书政策以腾讯云当期规则为准。

### 2.2 安全组

仅配置以下入站规则：

| 端口 | 来源 | 用途 |
| --- | --- | --- |
| 22/TCP | 管理员固定公网 IP | SSH，禁止全网长期开放 |
| 80/TCP | `0.0.0.0/0`、`::/0` | 证书签发和跳转 HTTPS |
| 443/TCP | `0.0.0.0/0`、`::/0` | 网站 HTTPS |

不要放行 3000、5432、6379。SSH 使用密钥登录，禁用 root 密码登录，并在腾讯云控制台开启主机安全和登录告警。

### 2.3 基础系统

```bash
sudo apt update && sudo apt upgrade -y
sudo timedatectl set-timezone Asia/Shanghai
sudo apt install -y nginx certbot postgresql-client curl ca-certificates openssl gnupg git rsync
```

Ubuntu 22.04 默认 Node.js 版本不满足要求。使用 NodeSource 签名仓库安装 Node.js 22，并校验实际二进制：

```bash
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://deb.nodesource.com/gpgkey/nodesource-repo.gpg.key \
  | sudo gpg --dearmor --yes -o /etc/apt/keyrings/nodesource.gpg
echo 'deb [signed-by=/etc/apt/keyrings/nodesource.gpg] https://deb.nodesource.com/node_22.x nodistro main' \
  | sudo tee /etc/apt/sources.list.d/nodesource.list
sudo apt update
sudo apt install -y nodejs
/usr/bin/node --version
/usr/bin/npm --version
```

2 GB 内存建议增加 2 GB swap，避免首次前端构建或依赖安装被 OOM 终止；swap 不能替代内存监控。

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

## 3. 生产环境变量

复制模板并限制读取权限：

```bash
cp .env.example .env
chmod 600 .env
```

必须设置的敏感项：

```bash
# URL 安全的数据库和 Redis 密码
openssl rand -hex 32
openssl rand -hex 32

# 访问令牌签名密钥与邮箱验证码 HMAC 密钥（必须分别生成）
openssl rand -base64 48
openssl rand -base64 48

# admin 初始密码
printf '%sAa1!\n' "$(openssl rand -base64 24 | tr -d '\n')"
```

将生成结果分别填入 `POSTGRES_PASSWORD`、`REDIS_PASSWORD`、`ACCESS_TOKEN_SECRET`、`EMAIL_VERIFICATION_HMAC_SECRET` 和 `ADMIN_PASSWORD`。管理员密码命令追加的 `Aa1!` 确保满足大小写字母、数字和特殊字符规则。不要把命令输出粘贴到工单、截图或 Git。环境名以当前代码为准：使用 `ACCESS_TOKEN_SECRET`、`ADMIN_EMAIL` 和 `ADMIN_PASSWORD`，不要使用旧名称 `JWT_SECRET`、`ADMIN_USERNAME` 或 `ADMIN_INITIAL_PASSWORD`。

### 3.1 QQ/163 邮箱 SMTP

注册和邮箱找回密码都依赖 SMTP。先在 QQ 邮箱或 163 邮箱的账号设置中开启 SMTP 服务并生成独立授权码；`SMTP_PASS` 填写的是该授权码，不是邮箱网页登录密码。建议为项目单独申请发件邮箱，避免与个人邮箱混用。

QQ 邮箱配置：

```env
SMTP_HOST=smtp.qq.com
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=项目发件邮箱@qq.com
SMTP_PASS=邮箱服务商生成的SMTP授权码
SMTP_FROM_NAME=农芯智境
```

163 邮箱配置：

```env
SMTP_HOST=smtp.163.com
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=项目发件邮箱@163.com
SMTP_PASS=邮箱服务商生成的SMTP授权码
SMTP_FROM_NAME=农芯智境
```

将 `ADMIN_EMAIL` 设置为受控的管理员邮箱。SMTP 测试脚本会随正式构建打包，不依赖生产容器中的开发工具。使用 Docker Compose 时先构建镜像再从一次性应用容器测试；宿主机方式则在 `npm run build` 后测试：

```bash
# Docker Compose
docker compose build app
docker compose run --rm --no-deps app node dist/smtp-smoke.mjs

# 宿主机（已经执行 npm ci 和 npm run build）
npm run smtp:smoke
```

该命令只发送到 `ADMIN_EMAIL`，不会在终端打印验证码、SMTP 授权码或完整配置。管理员收到“农芯智境邮箱验证码”邮件、版式正常且包含“五分钟内有效”提示后，才允许继续上线。测试失败时检查邮箱是否开启 SMTP、授权码是否过期、465 端口出站是否可用；不要把 `.env` 或失败日志中的敏感信息发到公开群聊。

关键配置说明：

- `SAAS_COOKIE_SECURE=true`：HTTPS 下必须开启。
- `PAYMENT_MODE=mock`：仅竞赛演示使用模拟结算；公开运营前设为 `disabled`，直到接入支付回调签名校验。
- Docker Compose 使用 `TRUST_PROXY=1`，只信任与应用直连的一跳 Docker/Nginx 代理；应用端口同时只绑定宿主机回环地址，外部不能绕过代理。宿主机 systemd 使用 `TRUST_PROXY=loopback`，只信任本机 Nginx。不要设为 `true` 或任意网段，否则攻击者可能伪造客户端 IP 并绕过限流。
- `DATABASE_POOL_MAX=8`：适配 2 核 2 GB 单机。
- `ADMIN_EMAIL=管理员邮箱`：应用首次启动时创建或提升唯一的最高权限账号，界面显示名固定为 `admin`。首次成功创建并确认能登录后，可从运行环境同时移除 `ADMIN_EMAIL` 和 `ADMIN_PASSWORD` 再重启；数据库中的账号和原密码仍有效。普通用户支持邮箱找回密码；管理员仍应使用独立强密码并保护邮箱，真实商用前再增加 MFA。
- AI 密钥按需填写；未使用的供应商密钥保持为空。

## 4. 推荐方式：Docker Compose

安装 Docker Engine 与 Compose v2 后，在项目目录执行：

```bash
docker compose config --quiet
docker compose build
docker compose up -d
docker compose ps
docker compose logs --tail=200 app
curl --fail http://127.0.0.1:3000/api/health
```

后续 Compose 备份和恢复命令必须知道项目绝对路径。本文示例假定项目位于 `/opt/nongxinzhijing/current`；如果实际目录不同，先执行 `PROJECT_DIR="$(pwd -P)"` 记录真实路径，并在首次备份和 crontab 中显式使用该值。

Compose 包含 `app`、`postgres`、`redis` 三个服务。PostgreSQL 和 Redis 没有 `ports` 配置；应用只发布 `127.0.0.1:3000`。启动应用前会执行 `node dist/migrate.mjs`，数据库迁移成功后才启动网站。

单机 Compose 的机密来自权限为 `0600` 的 `.env`，仅主机 root 和 Docker 管理员可读取；具备 Docker 管理权限的用户本身等同 root，也可能通过容器检查环境变量。该边界适合受控竞赛主机，不等同于企业级秘密管理；商用迁移到腾讯云托管服务时应改用云密钥管理、短期凭据和最小权限角色。

持久化卷：

- `postgres_data`：SaaS PostgreSQL 数据。
- `redis_data`：Redis AOF 数据。
- `app_data`：旧模块 JSON 数据，对应容器内 `/app/.data`。

常用操作：

```bash
# 更新版本
git pull --ff-only
docker compose build app
docker compose up -d

# 单独执行数据库迁移
docker compose run --rm app node dist/migrate.mjs

# 查看状态与日志
docker compose ps
docker compose logs -f --tail=200 app postgres redis

# 停止但保留数据卷
docker compose down
```

不要执行 `docker compose down -v`，它会删除数据卷。

## 5. 备选方式：宿主机 PostgreSQL、Redis 与 systemd

如果按腾讯云主机方式直接安装 PostgreSQL 和 Redis：

```bash
sudo apt install -y postgresql postgresql-contrib redis-server
sudo systemctl enable --now postgresql redis-server
```

确保 PostgreSQL 的 `listen_addresses = 'localhost'`，`pg_hba.conf` 只允许本地地址；Redis 配置包含 `bind 127.0.0.1 ::1`、`protected-mode yes` 和强密码。应用的 `DATABASE_URL`、`REDIS_URL` 均使用 `127.0.0.1`，不要写公网 IP。为应用创建专用数据库角色，不要让应用使用 PostgreSQL 超级用户。

宿主机 `.env` 还必须填写完整连接串，例如 `DATABASE_URL=postgresql://nxzj_app:实际URL安全密码@127.0.0.1:5432/agri_saas` 和 `REDIS_URL=redis://:实际URL安全密码@127.0.0.1:6379/0`。Compose 会覆盖这两项为容器服务名，无需手工改成容器地址。

安装 Node.js 22，确认 `/usr/bin/node --version` 输出 `v22`。创建独立系统账号、源码目录和发布目录：

```bash
sudo useradd --system --home /opt/nongxinzhijing --shell /usr/sbin/nologin nongxinzhijing
sudo mkdir -p /opt/nongxinzhijing/{releases,shared}
sudo mkdir -p /srv/nongxinzhijing-source
sudo chown -R nongxinzhijing:nongxinzhijing /opt/nongxinzhijing
sudo install -o root -g nongxinzhijing -m 0640 .env /opt/nongxinzhijing/shared/.env
```

管理员先把已审核的 Git 工作副本同步到 `/srv/nongxinzhijing-source`。每次发布创建不可变 release，记录原版本，复制源码、构建、安装生产依赖并校正所有权：

```bash
cd /srv/nongxinzhijing-source
git pull --ff-only

release_id="$(date +%Y%m%d%H%M%S)"
release_dir="/opt/nongxinzhijing/releases/$release_id"
previous_release="$(readlink -f /opt/nongxinzhijing/current || true)"
echo "previous_release=$previous_release"

sudo install -d -o nongxinzhijing -g nongxinzhijing -m 0750 "$release_dir"
sudo rsync -a --delete \
  --exclude='.git' --exclude='.env' --exclude='node_modules' --exclude='dist' \
  ./ "$release_dir/"
sudo chown -R nongxinzhijing:nongxinzhijing "$release_dir"

cd "$release_dir"
sudo -u nongxinzhijing npm ci
sudo -u nongxinzhijing npm run lint
sudo -u nongxinzhijing npm test
sudo -u nongxinzhijing npm run build
sudo -u nongxinzhijing npm ci --omit=dev
```

生产迁移已打包为 `dist/migrate.mjs`，SQL 位于 `dist/migrations`，运行时不依赖 `tsx`。检查构建产物后，用临时链接加原子重命名切换 `current`，再安装和重启服务：

```bash
test -f "$release_dir/dist/server.cjs"
test -f "$release_dir/dist/public/index.html"
test -f "$release_dir/dist/migrate.mjs"

sudo ln -sfn "$release_dir" /opt/nongxinzhijing/current.next
sudo mv -Tf /opt/nongxinzhijing/current.next /opt/nongxinzhijing/current
sudo cp "$release_dir/deploy/systemd/nongxinzhijing.service" /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now nongxinzhijing
sudo systemctl restart nongxinzhijing
sudo systemctl status nongxinzhijing --no-pager
journalctl -u nongxinzhijing -n 200 --no-pager
curl --fail http://127.0.0.1:3000/api/health
```

systemd 的 `ExecStartPre` 会在每次启动前安全执行数据库迁移；迁移失败时应用不会启动。旧业务数据写入 `/var/lib/nxzj`，由 `StateDirectory` 创建，并由安全沙箱限制为唯一可写业务目录。

生产端口被占用时服务会直接失败，不会切换到随机端口，避免 Nginx 代理到错误进程。

应用验证失败时，使用发布前记录的路径原子回滚代码。示例中的 `rollback_release` 必须替换为实际上一版本；数据库迁移只向前执行，若新版本包含不兼容迁移，应先按该版本的专用数据库回滚方案处理：

```bash
rollback_release="/opt/nongxinzhijing/releases/上一版本时间戳"
test -d "$rollback_release"
sudo ln -sfn "$rollback_release" /opt/nongxinzhijing/current.rollback
sudo mv -Tf /opt/nongxinzhijing/current.rollback /opt/nongxinzhijing/current
sudo cp "$rollback_release/deploy/systemd/nongxinzhijing.service" /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl restart nongxinzhijing
readlink -f /opt/nongxinzhijing/current
curl --fail http://127.0.0.1:3000/api/health
```

## 6. Nginx 与 HTTPS

首次签发证书前确认 80/443 已开放、DNS 已生效。standalone 模式续期时必须暂时释放 80 端口，因此先安装成对的 pre/post hooks；pre 只在 Nginx 原本运行时写入状态标记并停止，post 只在存在标记时重新启动：

```bash
sudo install -D -m 0755 deploy/certbot/hooks/pre/stop-nginx.sh \
  /etc/letsencrypt/renewal-hooks/pre/stop-nginx.sh
sudo install -D -m 0755 deploy/certbot/hooks/post/start-nginx.sh \
  /etc/letsencrypt/renewal-hooks/post/start-nginx.sh

sudo systemctl stop nginx
if ! sudo certbot certonly --standalone \
  --cert-name nongxinzhijing.site \
  -d nongxinzhijing.site \
  -d www.nongxinzhijing.site \
  --expand; then
  sudo systemctl start nginx
  exit 1
fi
sudo cp deploy/nginx/nongxinzhijing.conf /etc/nginx/conf.d/
sudo nginx -t
sudo systemctl enable --now nginx
sudo systemctl enable --now certbot.timer
```

验证自动续期和站点：

```bash
sudo certbot renew --dry-run
systemctl is-active nginx
curl -I http://www.nongxinzhijing.site
curl -I https://www.nongxinzhijing.site
```

dry-run 前后 Nginx 都应恢复为 `active`。如果续期失败且 Nginx 未恢复，先检查 `/run/nongxinzhijing-certbot-stopped-nginx` 和 Certbot 日志，再执行 `sudo systemctl start nginx`。HTTP 应返回 301 到 `https://www.nongxinzhijing.site`。配置已支持 `/api/ws` WebSocket 升级、指纹静态资源 30 天缓存、登录/注册/发送验证码/重置密码低速限流、刷新令牌独立限流和 HSTS；限流拒绝统一返回 429。

## 7. PostgreSQL 自动备份

宿主机 PostgreSQL 与 Compose PostgreSQL 的网络边界不同，必须使用对应方案。两种方案都生成 custom 格式、SHA-256 校验和并执行保留期清理；密码不写在脚本或命令行参数中。

### 7.1 宿主机 PostgreSQL

`deploy/scripts/pg_backup.sh` 只适用于宿主机直接安装的 PostgreSQL。密码存入 root 专用 `.pgpass`：

```bash
sudo install -d -m 0700 /etc/nongxinzhijing
sudoedit /etc/nongxinzhijing/pg_backup.pgpass
# 格式：127.0.0.1:5432:agri_saas:nxzj_app:实际数据库密码
sudo chmod 600 /etc/nongxinzhijing/pg_backup.pgpass

sudo install -m 0750 deploy/scripts/pg_backup.sh /usr/local/sbin/nxzj-pg-backup
sudo /usr/local/sbin/nxzj-pg-backup
```

设置每天 02:15 执行：

```bash
sudo crontab -e
# 添加：
15 2 * * * /usr/local/sbin/nxzj-pg-backup >>/var/log/nxzj-pg-backup.log 2>&1
```

本机备份默认位于 `/var/backups/nongxinzhijing/postgresql`，保留 14 天。单机磁盘上的备份不能应对磁盘损坏，至少每周复制到另一台设备。启用 COS 时，先用受限子账号配置 `coscmd`，仅授予目标备份路径的上传权限，再通过定时任务环境设置 `COS_BUCKET` 和 `COS_REMOTE_PREFIX`。COS 密钥不得写入仓库、脚本或截图。

### 7.2 Docker Compose PostgreSQL

Compose 没有发布数据库端口，所以宿主机脚本不能连接 `127.0.0.1:5432`。Compose 备份不需要开放 5432。安装专用 root 脚本，确保创建目录、重定向、校验、保留期清理和可选 COS 上传全部在同一权限边界内执行：

```bash
sudo install -m 0750 deploy/scripts/compose_pg_backup.sh \
  /usr/local/sbin/nxzj-compose-pg-backup
PROJECT_DIR="$(pwd -P)"
sudo env PROJECT_DIR="$PROJECT_DIR" /usr/local/sbin/nxzj-compose-pg-backup
sudo sh -c 'PROJECT_DIR=/opt/nongxinzhijing/current /usr/local/sbin/nxzj-compose-pg-backup'
```

脚本使用容器内 Unix socket 和容器已有环境，不在命令行展开数据库密码，也不映射 5432。加入每日 root 定时任务：

```bash
sudo crontab -e
# 添加：
15 2 * * * PROJECT_DIR=/opt/nongxinzhijing/current /usr/local/sbin/nxzj-compose-pg-backup >>/var/log/nxzj-compose-pg-backup.log 2>&1
```

如需 COS，在完成本地 SHA-256 校验后调用已配置受限子账号的 `coscmd upload` 上传 `.dump` 和 `.sha256`，上传成功日志纳入每日巡检；COS 密钥仍只保存在 root 权限配置中。本地保留 14 天，COS 建议按 30 至 90 天生命周期管理，并至少每月下载一份做恢复演练。

同时备份旧模块数据：Docker 模式备份 `app_data` 卷，systemd 模式备份 `/var/lib/nxzj`。建议使用腾讯云快照或 COS，并进行加密。

## 8. 恢复演练

至少每月在隔离数据库执行一次恢复演练，并记录用时和结果：

```bash
# 1. 校验文件完整性
sha256sum --check agri_saas.dump.sha256

# 2. 创建隔离恢复库
createdb -h 127.0.0.1 -U postgres agri_saas_restore

# 3. 恢复并检查关键表
pg_restore -h 127.0.0.1 -U postgres \
  --dbname=agri_saas_restore --clean --if-exists --no-owner agri_saas.dump
psql -h 127.0.0.1 -U postgres -d agri_saas_restore \
  -c 'select count(*) from users;'
```

正式恢复时先公告维护、停止应用、额外备份当前数据库，再恢复到新数据库并切换 `DATABASE_URL`；不要直接覆盖唯一生产库。恢复后运行 `node dist/migrate.mjs`、启动应用，并验证登录、授权、服务市场订单和健康检查。

Compose 恢复演练同样保持 PostgreSQL 私网隔离，不开放或映射 5432。以下命令全部以 root 执行，先校验可搬迁的 basename 校验和，再恢复到隔离库 `agri_saas_restore_compose`：

```bash
sudo sh -c '
set -eu
PROJECT_DIR=/opt/nongxinzhijing/current
cd "$PROJECT_DIR"
backup_dir=/var/backups/nongxinzhijing/postgresql/替换为备份时间戳
(cd "$backup_dir" && sha256sum --check agri_saas.dump.sha256)
docker compose exec -T postgres dropdb --if-exists --username=nxzj_app agri_saas_restore_compose
docker compose exec -T postgres createdb --username=nxzj_app agri_saas_restore_compose
docker compose exec -T postgres pg_restore --username=nxzj_app \
  --dbname=agri_saas_restore_compose < "$backup_dir/agri_saas.dump"
docker compose exec -T postgres psql --username=nxzj_app \
  --dbname=agri_saas_restore_compose -c "select count(*) from users;"
'
```

发布前门禁：


每次发布保留上一个 release 目录和数据库备份。代码回滚只需把 `current` 软链接指回上一版本并重启；数据库迁移默认只向前执行，涉及破坏性迁移时必须另写兼容、备份和回滚方案。禁止在未备份时手工修改生产表。

## 10. 监控与故障处理

| 现象 | 检查与处理 |
| --- | --- |
| 502 Bad Gateway | `curl 127.0.0.1:3000/api/health`，再查应用日志、端口占用和 Nginx error log |
| 应用启动失败 | 查看 `journalctl -u nongxinzhijing` 或 `docker compose logs app`；重点检查必填环境变量和迁移错误 |
| 数据库连接失败 | 检查 PostgreSQL 健康状态、`DATABASE_URL`、本机监听和磁盘空间；不要临时开放 5432 |
| Redis 连接失败 | 检查服务状态、密码和 `REDIS_URL`；不要临时开放 6379 |
| 登录频繁 429 | 检查是否遭遇暴力尝试；核对 Nginx/auth 与应用层限流日志，不要直接关闭限流 |
| AI 功能不可用 | 检查供应商余额、网络和对应密钥；日志中不得打印密钥 |
| 磁盘接近满 | 检查 PostgreSQL、Docker、日志和备份保留；先扩容或安全归档，不要直接删除数据库文件 |
| 内存不足 | 检查 `free -h`、`docker stats`；降低并发/连接池并扩容，不能依赖频繁重启 |
| 证书异常 | 检查 `certbot renew --dry-run`、DNS、80 端口及证书到期时间 |

建议接入腾讯云云监控：CPU、内存、磁盘使用率、进程存活、HTTPS 可用性和证书到期告警。数据库每日备份成功与失败都应有可追踪日志。
