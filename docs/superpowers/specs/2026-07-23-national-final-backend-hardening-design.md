# 农芯智境国赛版后端重构与真实 SaaS 设计

## 1. 文档状态

- 日期：2026-07-23
- 目标版本：2026 年中国大学生计算机设计大赛国赛演示版
- 部署域名：`https://www.nongxinzhijing.site`
- 设计结论：保留现有前端视觉语言和核心业务功能，采用模块化单体架构渐进重构后端
- 数据方案：线上使用公开数据回放与数字孪生模拟，离线保留等价演示数据
- 账号结论：邮箱是唯一登录账号，`admin` 是预置的超级管理员显示名称

## 2. 目标与验收结果

本轮工作不重新设计产品，而是把现有演示型系统完善为可注册、可登录、可授权、可审计、可恢复、可公开部署的真实 SaaS。

完成后必须呈现以下结果：

1. 新用户使用真实邮箱验证码完成注册。
2. 注册成功后自动获得个人组织和免费基础版权益。
3. 所有用户都能看到系统的完整功能入口。
4. 免费功能可以直接使用；未开通模块允许查看介绍或示例，但关键操作由后端拒绝。
5. 用户可以在服务市场提交模块开通申请。
6. 超级管理员审核后，权益立即生效并带有明确期限。
7. `admin` 默认拥有全部模块、无限演示额度和运营管理权限。
8. 普通用户不能通过修改前端状态、地址或请求参数绕过权限。
9. PostgreSQL 是用户、订单、权益及业务数据的唯一事实来源。
10. Redis 只保存短期数据；Redis 故障不能造成订单或权益丢失。
11. 外部 AI、SMTP 或公开数据源异常时，网站可以明确降级，国赛演示仍能继续。
12. 线上版本可以持续更新，并且每次发布均能回滚到上一个可用版本。

## 3. 明确边界

### 3.1 保留内容

- 保留现有产品名称、视觉风格、页面结构和主要导航习惯。
- 保留数字孪生、农田监测、AI 识别、知识问答、农业资讯、设备控制和服务市场等现有业务能力。
- 保持现有主要页面的操作含义，避免国赛前重新学习整套界面。
- 兼容现有前端调用方式，在后端迁移期间通过适配层维持响应字段。

### 3.2 允许的前端调整

前端不是完全冻结，而是“总体样式不变、必要状态补齐”。允许调整：

- 注册页增加邮箱验证码输入框、发送按钮、倒计时和错误提示。
- 登录框明确提示使用邮箱登录。
- 服务市场增加申请状态、有效期和已开通状态。
- 锁定功能增加统一升级提示。
- 管理员登录后增加仅管理员可见的运营管理入口。
- 修复布局、反馈、加载、空状态、错误状态和性能问题。

不得大规模更换配色、品牌、导航结构或核心业务页面布局。

### 3.3 本轮不做

- 不接入真实微信支付或支付宝资金交易。
- 不声称接入真实农业设备、真实农场或真实农业专家。
- 不拆分微服务，不引入 Kubernetes。
- 不建设超大规模物联网时序平台。
- 不把模拟数据描述成真实传感器实测数据。

## 4. 方案选择

### 4.1 已选择：渐进式后端替换

在现有系统旁建立清晰的业务模块和 PostgreSQL 数据模型，先迁移账号、权限、订单和权益，再迁移农场、监测、设备、AI、知识库与资讯数据。旧接口在迁移期由兼容层转发，新旧结果经过自动测试比对后再切换。

优点：

- 不破坏已经可以演示的前端。
- 每迁移一个模块就可以单独验证和回滚。
- 适合国赛前持续发布。
- 能复用已经完成的 SaaS 基础和测试。

### 4.2 未选择：一次性重写

一次性重写结构更整齐，但国赛前风险过高，容易产生大量前后端联调问题。

### 4.3 未选择：继续修补 JSON 后端

短期改动少，但无法可靠支撑并发注册、订单事务、多租户隔离、审计与恢复，不符合真实 SaaS 的最低要求。

## 5. 总体架构

系统部署为模块化单体，一个后端应用进程按业务边界组织代码：

- `auth`：邮箱验证码、注册、登录、刷新、退出、找回密码。
- `organizations`：个人组织、成员和组织级数据隔离。
- `catalog`：套餐、模块、价格展示和服务市场目录。
- `billing`：开通申请、订单状态和管理员审核。
- `entitlements`：模块授权、有效期、额度和管理员覆盖。
- `farms`：农场、地块和作物。
- `monitoring`：监测数据、告警和公开数据回放。
- `devices`：设备状态、控制命令和模拟适配器。
- `ai`：识别、问答、决策请求、缓存、配额和降级。
- `content`：知识库与农业资讯。
- `audit`：安全事件和关键业务操作日志。
- `operations`：健康检查、任务状态、发布与恢复信息。

模块只能通过公开服务接口协作，不能直接修改其他模块的私有数据。前端继续通过同一个域名访问 REST API 和 WebSocket，不增加跨域部署复杂度。

## 6. 邮箱注册与登录

### 6.1 账号规则

- 邮箱是普通用户和管理员的唯一登录标识。
- 邮箱在服务端执行去空格和小写标准化，并建立唯一索引。
- 用户显示名称可以是昵称；`admin` 只是超级管理员的显示名称，不是第二套用户名登录方式。
- 普通注册请求永远不能指定平台角色或管理员角色。
- 注册成功时在一个数据库事务中创建用户、个人组织、`owner` 成员关系和免费订阅。

### 6.2 验证码流程

1. 用户输入邮箱并请求验证码。
2. 后端生成六位数字验证码，使用安全随机数，不使用可预测序列。
3. Redis 只保存验证码摘要、用途、失败次数和到期时间，不保存明文。
4. 验证码有效期为 5 分钟。
5. 同一邮箱 60 秒内不能重复发送。
6. 同一邮箱每小时最多发送 5 次，同一 IP 每小时最多发送 20 次。
7. 同一验证码连续输错 5 次立即失效。
8. 验证成功后验证码立即作废，不能重复注册。
9. 发送接口使用统一响应，避免通过接口探测邮箱是否已注册。
10. Redis 不可用时停止签发验证码并返回可重试提示，不降级为固定验证码或前端验证码。

### 6.3 SMTP 邮件

- 后端通过统一邮件适配器发送，不由用户提交 SMTP 配置。
- 支持通过环境变量切换 QQ 邮箱或 163 邮箱 SMTP。
- 使用邮箱服务提供的授权码，不使用网页登录密码。
- SMTP 主机、端口、发件邮箱、授权码、发件名称和 TLS 策略全部由服务器环境变量提供。
- 日志只记录投递结果、耗时、邮件模板版本和脱敏收件地址，不记录验证码或 SMTP 授权码。
- 邮件发送失败时不生成可用验证码，前端显示“邮件暂未发送成功，请稍后重试”。
- 邮件模板包含产品名称、验证码、5 分钟有效期、安全提醒和官方域名。

### 6.4 密码与会话

- 密码至少 8 位，必须同时包含字母和数字。
- 密码使用 bcrypt 哈希，数据库不保存明文或可逆密文。
- 登录失败使用邮箱与 IP 双维度限流。
- 访问令牌短期有效；刷新令牌以 HttpOnly、Secure、SameSite Cookie 传输，数据库只保存其哈希。
- 退出登录、修改密码、重置密码或管理员停用账号后，相关会话失效。
- 找回密码复用 SMTP 验证能力，但使用独立用途和独立验证码，不能与注册验证码混用。

## 7. 管理员体系

### 7.1 超级管理员

首次部署通过受保护的服务器配置创建超级管理员：

- 显示名称：`admin`
- 登录标识：部署时配置的真实管理员邮箱
- 平台角色：`platform_admin`
- 权益：全部功能、无演示额度限制
- 能力：用户查询、账号停用、商品维护、订单审核、权益查询、授权撤销和审计查看

系统不得在公开注册页创建超级管理员。生产环境不存在固定后门密码，也不允许通过前端参数切换管理员身份。

### 7.2 管理入口

- 管理入口位于现有网站内部，仅管理员登录后展示。
- 隐藏菜单不是安全边界；每个管理接口都必须在后端校验 `platform_admin`。
- 普通用户直接访问管理地址时返回无权限页面，管理 API 返回标准 403。
- 高风险操作要求填写审核备注，并记录操作者、时间、目标、原状态和新状态。

## 8. 服务市场、订单与权益

### 8.1 用户流程

1. 用户可以看到全部模块及其免费、试用、专业版或已开通状态。
2. 用户选择模块和期限后提交开通申请。
3. 后端从商品目录读取价格和期限，生成不可篡改的订单快照。
4. 订单进入“待审核”，用户可以查看处理状态。
5. 管理员确认或拒绝申请。
6. 确认时在一个数据库事务内完成订单状态变更、权益发放和审计记录。
7. 用户重新取得权益信息后，模块立即解锁。

竞赛版不收取真实资金。页面使用“申请开通”或“申请试用”等准确措辞；商品价格可以展示，但不得让用户误以为已经完成线上扣款。未来接入支付平台时，由真实支付成功回调替代人工确认，权益发放逻辑保持不变。

### 8.2 订单状态

- `pending_review`：等待管理员审核。
- `fulfilled`：审核通过且权益已发放。
- `rejected`：审核拒绝。
- `cancelled`：用户在审核前取消。
- `expired`：待审核申请超过有效处理时间后自动关闭。
- `refunded`：未来真实支付场景保留。

审核接口使用幂等键并锁定订单行。重复点击、网络重试或重复请求不能重复发放权益。

模块使用期限只记录在订阅和权益中。权益到期不会把已经履行的订单改成 `expired`，系统只停止该模块的授权。

### 8.3 权益判断

后端统一按以下顺序判断：

`账号有效 → 组织有效 → 管理员覆盖 → 模块权益存在 → 当前时间未过期 → 使用额度未耗尽`

初始功能键包括：

- `monitoring.basic`
- `monitoring.realtime`
- `ai.diagnosis`
- `digital_twin.advanced`
- `analytics.advanced`
- `device.control`
- `team.members`
- `deployment.private`

免费基础版提供基础监测、知识库、有限地块数和有限 AI 次数。具体展示数量由服务端套餐配置提供，前端不得自行决定额度。

## 10. 现有数据渐进迁移

1. 冻结并记录现有前端所使用的 API 路径、字段、状态码和错误格式。
2. 备份当前 JSON 数据并计算校验值。
3. 使用可重复执行的导入程序将数据写入 PostgreSQL。
4. 迁移期间对关键只读接口执行新旧结果比对。
5. 按账号、农场、监测、设备、AI、知识与资讯的顺序切换读取来源。
6. 写操作切换后只写 PostgreSQL，不长期保留双写。
7. 每个阶段保留回滚开关和导入报告。
8. 全部验证通过后，JSON 仅作为只读归档，不再作为运行时数据库。

兼容层负责将新后端内部模型转换成现有前端需要的结构。内部可以重构，前端不因字段重命名而大面积修改。

## 11. Redis 使用与降级

Redis 用于：

- 邮箱验证码及发送频率控制。
- 登录和敏感接口限流。
- 短期会话辅助与撤销标记。
- AI 结果缓存、请求去重和短任务状态。
- 监测页面热点数据缓存。
- WebSocket 在线状态。

Redis 不保存用户、订单、权益或审计的唯一副本。Redis 故障时：

- 已登录用户的核心只读页面允许回源 PostgreSQL。
- 订单与权益仍以 PostgreSQL 为准。
- 验证码注册暂时停止并提示重试。
- 限流切换到进程内保守策略。
- AI 缓存失效但不能重复扣除成功额度。

## 12. AI、监测和设备的真实化处理

### 12.1 AI

- AI 密钥只存在服务器环境中。
- 每个请求设置超时、有限重试、结果缓存和熔断。
- 只有成功返回的请求才消耗成功额度。
- 结果记录模型、版本、耗时、数据来源和生成时间。
- AI 不可用时返回清晰的降级结果，不伪造实时模型调用。
- 上传文件限制类型、大小、数量和组织归属。

### 12.2 公开数据与演示数据

- 线上允许使用公开数据回放和数字孪生模拟驱动现有监测界面。
- 页面以“公开数据”“模拟数据”或“AI 生成建议”明确标注来源。
- 数据提供器统一输出现有页面所需结构，前端业务功能不随来源变化。
- 公开接口失效时自动切换到最近一次合法缓存。
- 离线包包含同结构、固定版本、可复现的演示数据。

### 12.3 设备控制

- 没有真实设备时，命令进入模拟设备适配器。
- 每条控制命令生成唯一编号并记录发起人、设备、参数、时间和结果。
- 重复请求不能重复执行。
- 前端必须显示“模拟设备”状态，不能声称已控制真实硬件。
- 将来接入硬件时只替换设备适配器，不修改权限、命令和审计流程。

## 13. 错误处理与用户反馈

所有 API 使用统一错误结构，至少包含稳定错误码、用户可读信息和请求追踪编号。

关键场景：

- SMTP 失败：验证码不生效，提示稍后重试。
- 验证码错误或过期：明确区分可重试与必须重新发送。
- PostgreSQL 不可用：写请求失败，不静默写入浏览器或 JSON。
- Redis 不可用：按第 11 节降级。
- AI 不可用：展示暂不可用或缓存结果，不扣成功额度。
- 权益不足：返回 403 和缺少的功能键，前端打开统一升级提示。
- 订单重复审核：返回当前订单状态，不重复授权。
- 外部数据失败：使用带时间标记的缓存或离线数据。

日志不得包含密码、验证码、令牌、SMTP 授权码、完整 AI 密钥或用户上传原图。

## 14. 安全设计

- PostgreSQL 和 Redis 仅监听本机，不在腾讯云安全组开放 5432、6379。
- 对外只开放 80、443；22 仅允许可信来源地址。
- 全站 HTTPS，HTTP 自动跳转 HTTPS。
- 使用安全响应头、严格来源校验、请求体大小限制和上传白名单。
- 所有 SQL 使用参数化查询。
- 所有资源访问进行组织归属校验，防止水平越权。
- 管理接口、设备控制、AI 请求和验证码接口分别限流。
- 关键操作写入不可由普通用户修改的审计日志。
- 生产密钥从环境变量注入，`.env` 不进入版本库和构建产物。
- 管理员首次登录后必须更换初始化密码。

## 15. 腾讯云部署

目标服务器为 Ubuntu 22.04、2 核 CPU、2GB 内存、40GB 系统盘。采用适合该规格的单机部署：

- Nginx：HTTPS、静态资源、反向代理、压缩和缓存。
- Node.js 应用：监听 `127.0.0.1`，单进程运行。
- PostgreSQL：监听 `127.0.0.1:5432`，使用项目专用非超级用户。
- Redis：监听 `127.0.0.1:6379`，启用认证和内存上限。
- 进程由现有容器编排和发布脚本管理。

域名 `www.nongxinzhijing.site` 配置有效证书。发布过程为：

`构建并测试 → 数据库备份 → 执行迁移 → 启动新版本 → 健康检查 → 切换流量 → 保留旧版本`

健康检查失败时自动恢复旧应用版本；数据库迁移采用向后兼容策略，不依赖破坏性自动回滚。

## 16. 备份与恢复

- PostgreSQL 每日生成压缩备份。
- 本机保留 7 个日备份，并保存至少一个异地加密副本。
- 备份目录仅部署账户和备份任务可访问。
- 数据库密码不直接写入可公开读取的脚本。
- 每周执行备份文件完整性检查。
- 国赛前至少完成一次在空数据库中的完整恢复演练并记录耗时。
- 发布前额外生成一次数据库备份。

## 17. 测试方案

### 17.1 自动测试

必须覆盖：

- 邮箱标准化和唯一性。
- 验证码有效期、发送间隔、小时限额、错误次数和一次性使用。
- SMTP 成功、失败、超时和重试边界。
- 普通注册不能创建管理员。
- 密码哈希、登录、刷新、退出和找回密码。
- 不同组织之间的数据隔离。
- 免费用户能看到模块但不能调用受控接口。
- 管理员拥有全部功能和无限演示额度。
- 开通申请、拒绝、确认、到期和撤销。
- 重复审核只发放一次权益。
- Redis 故障和 AI 故障降级。
- JSON 到 PostgreSQL 导入的数量与关键字段校验。
- 数据库迁移、备份和恢复。

### 17.2 端到端验收

至少自动或人工验证三条完整路径：

1. 新邮箱收验证码、注册、登录并获得免费版。
2. 普通用户申请模块、管理员审核、用户立即解锁。
3. 断开外部网络后，预置演示账号仍能使用离线数据完成核心演示。

还要执行类型检查、生产构建、现有回归测试、关键接口并发测试、依赖安全扫描和浏览器兼容检查。

## 18. 国赛演示保障

现场准备两套入口：

- 线上主入口：真实域名、真实邮箱验证码、公开数据回放和完整管理员审核流程。
- 离线备用：预置普通用户、预置 `admin`、固定演示数据和相同页面流程。

推荐现场闭环：

`邮箱注册 → 免费版登录 → 查看锁定模块 → 服务市场提交申请 → admin 审核 → 用户模块立即解锁 → 展示 AI/数字孪生结果与审计记录`

离线模式不得提供万能验证码或公开后门。备用账号在赛前创建并测试，密码单独保管。

## 19. 实施顺序

1. 固化 API 兼容契约和现有测试基线。
2. 完成邮箱验证码、唯一邮箱登录和找回密码。
3. 完善管理员预置、用户状态和会话安全。
4. 完善服务市场申请、人工审核、权益期限和审计。
5. 将剩余业务数据从 JSON 渐进迁移到 PostgreSQL。
6. 接入 Redis 的验证码、限流、缓存和降级。
7. 加固 AI、公开数据回放、模拟设备和离线数据提供器。
8. 完成统一错误反馈、性能与安全加固。
9. 完成腾讯云灰度发布、备份恢复和回滚验证。
10. 完成线上与离线两套国赛全流程彩排。

## 20. 最终验收标准

只有同时满足以下条件才视为完成：

- 前端品牌与核心使用习惯未被破坏。
- 真实邮箱验证码注册可在生产域名完成。
- 权限、订单和权益无法从前端绕过。
- `admin` 和普通用户的权限边界清晰。
- PostgreSQL、Redis、SMTP、AI 任一外部依赖异常都有确定结果。
- 线上和离线演示均能独立完成核心闭环。
- 自动测试、生产构建、数据恢复演练和发布回滚验证全部通过。
- 文档不把模拟设备、模拟数据或人工审核描述为真实硬件、实测数据或真实支付。
